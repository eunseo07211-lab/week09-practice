# 09주차 실습 패키지 · 대용량 검색·정렬·페이징 심화 과제 정리

## 1. 주요 개념 설명

* **오프셋 기반 페이징 (Offset-based Pagination)**
  * SQL의 `LIMIT`과 `OFFSET`을 사용하여 특정 번째 데이터부터 지정된 개수만큼 끊어서 조회하는 방식입니다. 사용자가 직관적인 페이지 번호(1페이지, 2페이지 등)를 통해 이동할 수 있는 장점이 있으나, 대용량 데이터 환경에서 `OFFSET`이 커질수록 데이터베이스가 앞쪽의 데이터를 전부 읽고 버려야 하므로 성능 저하(Offset Cache Thrashing)가 발생할 수 있습니다.
* **커서 기반 페이징 (Cursor-based / Keyset Pagination)**
  * 페이지 번호 대신 마지막으로 조회된 데이터의 고유 식별자(`id`)와 정렬 기준 값을 커서(`WHERE id < ?`)로 삼아 다음 데이터를 탐색하는 방식입니다. 데이터의 삽입과 삭제가 빈번해도 중복이나 누락(Cursor Shift)이 발생하지 않아 무한 스크롤 및 대용량 피드에 최적화되어 있습니다.
* **디바운스 (Debounce)**
  * 연속적인 이벤트 발생 시(예: 키보드 타이핑), 지정된 시간(300ms) 동안 추가 입력이 없을 때까지 이벤트 실행을 지연시키고 마지막 최종 입력 1회만 처리하는 최적화 기법입니다. 불필요한 서버 API 호출을 대폭 줄여 네트워크 부하를 방지합니다.
* **Race Condition (경쟁 상태) 및 AbortController**
  * 네트워크 지연 상황에서 사용자가 검색어를 빠르게 변경할 때, 먼저 보낸 느린 요청의 응답이 나중 요청보다 늦게 도착하여 화면을 오염시키는 현상입니다. `AbortController`를 통해 새로운 요청 발생 시 이전 미완료 `fetch` 요청을 즉시 강제 중단(`abort`)함으로써 데이터 정합성을 유지합니다.

## 2. 페이징 전략 비교 및 비동기 제어 역할

### ① 오프셋 페이징 vs 커서 페이징에 적합한 화면
* **오프셋 페이징 적합 화면**
  * 전통적인 게시판 목록, 관리자(Admin) 대시보드 등 총 데이터 건수가 고정되어 있고, 사용자가 특정 페이지 번호(예: 5페이지)로 직접 점프 이동해야 하는 인터페이스에 적합합니다.
* **커서 페이징 적합 화면**
  * 소셜 미디어 피드, 실시간 로그 시스템, 무한 스크롤(Infinite Scroll) 형태의 타임라인 등 데이터의 실시간 유입이 많고 오프셋 밀림 현상을 방지해야 하는 대용량 목록 화면에 적합합니다.

### ② 디바운스 및 요청 취소(AbortController)의 역할
* **디바운스의 역할 ("요청 횟수 자체를 사전에 줄이는 역할")**
  * 사용자가 검색창에 글자를 타이핑할 때 매 글자마다 서버로 요청이 폭주하는 것을 막고, 타이핑이 완료된 시점에 단 1회의 요청만 전송되도록 제어합니다.
* **요청 취소(AbortController)의 역할 ("이미 출발한 무효한 요청의 응답 꼬임을 방지하는 역할")**
  * 네트워크 지연 등으로 순서가 뒤엉킬 때, 이미 유효하지 않게 된 이전 요청의 응답이 최신 화면을 덮어쓰는 Race Condition을 원천 차단합니다.

## 3. 핵심 알고리즘 원리 및 계산식

### ③ limit + 1 원리 (커서 페이징 탐색)
* **동작 원리**
  * 클라이언트가 요청한 개수(`limit`, 예: 10개)보다 1개가 더 많은 총 `limit + 1`개(11개)의 데이터를 DB에서 조회합니다.
  * 조회된 결과의 개수가 `limit + 1`개이면 **"다음 페이지가 존재함 (`hasNext: true`)"**으로 판별하고, 실제 클라이언트에는 지정된 `limit`개(10개)만 슬라이싱하여 전달합니다.
  * 조회된 결과가 `limit`개 이하이면 **"마지막 페이지임 (`hasNext: false`)"**으로 판별하여 더 보기 버튼을 비활성화/숨김 처리합니다.

### ④ offset 및 totalPages 계산식
* **SQL OFFSET 계산식**
  * `offset = (page - 1) * limit`
  * *(예: 2페이지이고 limit이 10개라면, `(2 - 1) * 10 = 10`번째 데이터부터 건너뜀)*
* **전체 페이지 수 (totalPages) 계산식**
  * `totalPages = Math.ceil(totalCount / limit)`
  * *(전체 데이터 건수를 페이지당 표시 개수로 나눈 뒤 올림 처리하여 총 페이지 수 산출)*

## 4. AI 활용, 개발 난제 해결 및 직접 검증 내역

### (1) AI 협업 및 활용 범위
* **비동기 제어 구조 설계 보조**: `AbortController`를 이용한 중복 요청 취소 및 `AbortError` 예외 분기 처리(`try...catch`)의 표준 비동기 패턴 구조화 보조에 AI를 활용함.
* **SPA 라우팅 및 상태 동기화 보조**: `URLSearchParams`와 `window.history.pushState`, `popstate` 이벤트를 연동하여 주소창과 UI 상태(입력창, 정렬, 페이지)를 실시간으로 일치시키는 라우팅 로직 설계 보조에 활용함.

### (2) 개발 과정에서의 주요 기술적 난제(Troubleshooting) 및 해결 내용

* **① Race Condition (경쟁 상태) 및 비동기 지연 해결**
  * **문제점**: 네트워크 지연 환경(`Slow 3G`)에서 사용자가 검색어를 빠르게 연속 변경할 경우, 먼저 보낸 느린 요청의 응답이 나중에 보낸 요청의 응답보다 늦게 도착하여 화면이 잘못된 구형 데이터로 덮어씌워지는 데이터 꼬임 현상 발생 우려.
  * **해결 내용**: 각 `fetch` 요청마다 `AbortController` 시그널을 바인딩하고, 새로운 검색 요청 진입 시 이전 대기 중인 미완료 요청을 `.abort()`로 즉시 강제 중단하여 정합성을 확보함. 또한 `AbortError`를 명시적으로 예외 분기 처리하여 불필요한 콘솔 에러 전파를 방지함.

* **② 대용량 데이터 커서 페이징 고속 탐색 (`limit + 1` 전략)**
  * **문제점**: 대용량 데이터 환경에서 전체 데이터 개수를 세는 `COUNT(*)` 쿼리를 매번 수행하면 데이터베이스 연산 부하가 급증하는 성능 저하 문제 발생.
  * **해결 내용**: 클라이언트가 요청한 개수보다 1개 더 많은 `limit + 1`개를 조회하는 슬라이싱 전략을 도입하여, 전수 스캔 없이 다음 페이지 존재 여부(`hasNext`)를 밀리초(ms) 단위로 고속 판별하도록 백엔드 알고리즘을 최적화함.

* **③ 동적 정렬 파라미터 보안 및 프로토타입 오염 방지**
  * **문제점**: 브라우저 주소창을 통해 허용되지 않은 임의의 문자열이나 악의적인 상속 속성(`__proto__`, `constructor`), 그리고 SQL Injection 시도(`views; DROP TABLE--`)가 유입될 경우 서버가 에러를 내며 다운되거나 취약점에 노출될 위험 존재.
  * **해결 내용**: 엄격한 화이트리스트 검증 로직(`['latest', 'oldest', 'views'].includes()`)을 구현하여 비정상적인 입력이 유입되더라도 에러 없이 기본 정렬 기준인 최신순(`latest`, `id DESC`)으로 안전하게 폴백되도록 방어 로직을 구축함.

* **④ SPA 환경에서의 URL 상태 복원 동기화**
  * **문제점**: 페이지 이동이나 검색 후 브라우저의 '뒤로 가기' 버튼을 눌렀을 때, 주소창의 URL은 바뀌지만 실제 화면의 입력창(`input`), 정렬 선택 박스(`select`), 그리고 데이터 테이블 결과가 동기화되지 않고 어긋나는 현상 발생.
  * **해결 내용**: `popstate` 이벤트 리스너를 등록하여 뒤로 가기/앞으로 가기 발생 시 주소창의 쿼리 파라미터를 다시 파싱하여 UI 컨트롤러와 서버 데이터를 정확히 일치시키도록 라우팅 상태 복원 로직을 완성함.

### (3) 로컬 브라우저 환경 직접 검증 및 테스트 내역 (Troubleshooting 반영)

AI가 제안하거나 설계한 코드를 로컬 브라우저 환경에 직접 빌드 및 배포한 뒤, **개발자 도구(F12)**를 열어 다음 항목들을 직접 수행하고 철저히 검증함:

1. **네트워크 탭 (Network - Slow 3G 스로틀링을 통한 비동기 취소 확인)**: 
   * 로컬(`localhost`) 환경 특유의 초고속 응답 속도로 인해 비동기 요청 취소(`canceled`) 상태를 육안으로 포착하기 어려웠던 문제 발생.
   * **AI 자문 및 해결**: AI에게 원인을 문의하여 개발자 도구 Network 탭의 **Throttling 기능을 'Slow 3G'로 설정**하여 인위적인 네트워크 지연을 유발하는 방법을 적용함. 그 결과, 검색어를 연속 입력할 때 이전 요청이 대기(Pending) 상태에 머물다가 새로운 요청과 함께 `canceled` 상태로 정확히 소멸하는 과정을 명확하게 포착하고 검증함.
2. **콘솔 탭 (Console)**: 
   * 요청 취소 시 `[AbortController] 이전 비동기 요청이 정상 취소되었습니다.` 로그가 에러 없이 깨끗하게 출력되는지 직접 확인.
3. **보안 및 예외 테스트**: 
   * 주소창에 `?sort=__proto__`나 `?sort=views; DROP TABLE--` 같은 악의적인 파라미터를 직접 주입했을 때, 서버 다운 없이 `latest` 기준으로 안전하게 폴백되어 정상 렌더링되는지 검증함.
4. **라우팅 및 히스토리 테스트**: 
   * 페이지 이동 및 검색 후 브라우저 '뒤로 가기' 버튼을 눌렀을 때 URL 쿼리 스트링과 입력창, 정렬 상태, 데이터 목록이 정확히 일치하게 되돌아오는 것을 최종 확인 완료함.
 - **문장 표현력 및 구조화 협업**:
  - 대용량 데이터 페이징 알고리즘(`limit + 1`)과 비동기 제어 구조(`AbortController`, `디바운스`)의 개념적 배경을 체계적으로 정리하고 가독성을 높이는 문서 구조(목차 및 큰 틀의 뼈대) 설계에 AI(Gemini) 협업을 활용함.
- **주도적 검증 및 최종 완성**:
  - AI가 제안하고 보조한 설계 구조를 바탕으로, 로컬 개발 환경(VS Code, Git Bash)에서 소스 코드를 직접 빌드하고 `Slow 3G` 네트워크 스로틀링, 주소창 악성 파라미터 주입 테스트 등을 **본인이 직접 수행·검증**함.
  - 도출된 실제 테스트 결과와 트러블슈팅 인사이트를 바탕으로 모든 내용과 코드를 본인의 방식으로 전면 재검토 및 개선하여 최종 `README.md`를 완성함.
